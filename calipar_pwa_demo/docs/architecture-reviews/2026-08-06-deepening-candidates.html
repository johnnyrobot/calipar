Sequencing — the argument that decided it

Ship the defect fixes first, land the modules after. Fixing them removes the modules' headline justification, and that is the honest test of whether the modules are worth building: if nobody still wants the refactor afterwards, four commits were saved; if they do, it is being bought for locality alone, with eyes open. The fixes also give each migration a regression net that a test written afterwards cannot provide.

One decision blocks the Worker work

Are analyze, equity-check and socratic deliberate demo surface awaiting UI, or leftovers? Deleting them removes ~210 lines from worker/index.ts, dissolves candidate 5 entirely, and eliminates all three socratic fallthroughs by subtraction. It is a product decision, not an architectural one.

Problem

Session minting and verification are unexported, so 26 of 41 handleRequest calls round-trip an HTTP mint just to get a cookie, and the crypto can only be observed as a 401.

Solution

Move codec, HMAC, expiry stamping and cookie parsing behind mintSession / readSession, throwing plain errors mapped at the seam — the contract limits.ts, body.ts and stream.ts already use.

Verified: a test promises coverage that cannot exist

tests/worker/ai-worker.test.ts:574 is named "rejects tampered, expired-shaped, and malformed session cookies". Its three variants are ${cookie}tampered, missing-signature, bad.payload.extra. None is expired, and none can be — signSession always stamps Date.now() + SESSION_SECONDS and is unreachable from a test. The expiry branch at :412 is untested.

Wins

  • locality: one module owns session
  • expiry becomes testable at all
  • leverage: 26 tests drop a round-trip
  • kills mock.calls[1] index leak
  • deletes duplicated base64Url
  • clock injectable, per stream.ts

Deletion test: reappears — base64url codec, HMAC import, expiry stamping and checking, cookie parsing. base64Url is already copied verbatim into limits.ts:29-33; code with no home. Honest caveat: this is not a seam — one caller each, nothing varies. It earns its place as a test surface, following the limits/body/stream precedent, not by adapter count.

Problem

The same graph rules are written once per record on the write path and again over the whole workspace on import, so only one of them is the real definition of a valid workspace.

Solution

One workspace integrity module answers "does this record fit this workspace?" — consulted per-record by the write path and over the whole graph by import and reset.

Verified: the two implementations have already drifted

For a resource request, the write path (:515-535) resolves organizations.get(...) and fails on !organization. The import path (:733-746) never checks the organization exists — it infers it transitively through the review. The null-guard differs too: value.actionPlanId && versus request.actionPlanId !== null. Two implementations of one rule, already disagreeing about what a valid workspace is.

Wins

  • one definition of a valid workspace
  • write path and import path agree, provably
  • rules testable as plain values
  • largest block of Dexie tests needs no IndexedDB

Deletion test: reappears across four callers — three mutators re-inline their joins, import re-inlines the graph walk, the seed test re-inlines its hand check. Biggest test-surface win in the cluster: today the same rule needs a seeded Dexie database on the write side and a second database plus a fixture file on the import side. Contradicts no ADR.

Checked and found already deep — leave alone

lib/domain/derivations.ts — pure, WorkspaceData → WorkspaceDerivations, no Dexie in its tests, and its tests actively police ADRs 0002 and 0003. The benchmark for the rest of the cluster.

components/workspace-provider.tsx — deep on the read path; three states, one hook, two adapters, a self-consistent fixture.

worker/limits.ts, body.ts, stream.ts — each hides several failure modes behind two or three arguments and is tested without constructing a route. The precedent candidates 2 and 3 should extend.

handleRequest — (Request, Env) → Response over a 1400-line implementation. Textbook deep.

lib/domain/errors.ts — closed code union, one normalizer, tested as plain values. The module is fine; candidate 1's problem is that the write path never calls it.

lib/utils/sanitize.ts, lib/db/database.ts — both correctly small.

One vocabulary correction worth keeping

The optional trailing database argument on the 17 exported repository functions is not a seam — createDatabase(name) returns the same class under a different IndexedDB name, so there is one implementation and zero adapters. It is a test-isolation parameter, and a legitimate one. The only real seam in that cluster is useWorkspace().

Top recommendation

Start with the workspace commit.

It is the only candidate with defects already shipped rather than latent: a "Mission-Bot" filter button that can never match a record, and a raw DOMException reaching the user's notice line. It lands in lib/**, which the coverage gate measures — unlike the five repository callers in app/**, where every call-site defect was found. And it gives the write path the adapter the last review's candidate 3 only half-delivered, retiring three vi.mocks.

Then the demo session before the free-route policy — policy assertions cost a cookie and a fetch stub today, which is exactly what the session interface removes. Both extend a seam that already works: limits.ts, body.ts and stream.ts throw plain errors that index.ts maps onto the public AIErrorCode union.
